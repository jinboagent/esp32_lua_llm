# Stage 0 + Stage 1 综合评估报告 — 2026-07-21

## 一、Bug 发现

### 🔴 严重 (4 个)

#### B1. Pipeline 死代码 — `vTaskDelete(NULL)` 后 `s_pipeline_task` 永远不为 NULL

**文件**: `firmware/components/ble/scan_pipeline.c:72-74`
**影响**: Pipeline 停止后永远无法重新初始化

```c
vTaskDelete(NULL);        // ← 删除当前任务，永不返回
s_pipeline_task = NULL;   // ← 死代码！永远不会执行
```

`vTaskDelete(NULL)` 删除调用任务后不返回。`s_pipeline_task` 保持旧句柄（指向已删除的任务）。下次调用 `pipeline_init()` 时，检查 `s_pipeline_task != NULL` 为真 → 返回 `-811`（重复初始化错误）。

**修复**: 在 `pipeline_stop()` 中（而非任务退出时）将 `s_pipeline_task` 设为 NULL，或使用 `xTaskGetHandle("pipeline")` 动态查找。

---

#### B2. 过滤器从未接入 Pipeline

**文件**: `firmware/components/ble/scan_pipeline.c:51` + `main/main.c`
**影响**: 所有广播直接输出，过滤功能完全失效

Pipeline 中有过滤逻辑：
```c
// scan_pipeline.c:51
if (s_filter_engine != NULL) {
    if (!filter_evaluate(s_filter_engine, &parsed)) { ... }
}
```

但：
- `pipeline_init()` 总是设置 `s_filter_engine = NULL`
- 没有任何 `pipeline_set_filter()` API 来赋值
- `main.c` 中的 `s_filter_engine` 只在 CLI 用（FILTER CLEAR/LIST），从未传给 pipeline

**修复**: 添加 `pipeline_set_filter(filter_engine_t *eng)` API，在 `main.c:132` 后调用 `pipeline_set_filter(&s_filter_engine)`。

---

#### B3. NVS 擦除失败直接 `abort()` 崩溃

**文件**: `firmware/components/ble/ble_nimble_init.c:49`
**影响**: Flash 坏块导致系统崩溃重启而非优雅报错

```c
ESP_ERROR_CHECK(nvs_flash_erase());  // ← 失败时调用 abort()！
```

`ESP_ERROR_CHECK` 宏在 `ESP_ERR_*` 时调用 `assert(0)` / `abort()`。NVS 擦除失败（例如 flash 坏块）会导致整个系统崩溃。

**修复**: 改为手动错误检查：
```c
esp_err_t erase_err = nvs_flash_erase();
if (erase_err != ESP_OK) {
    printf("BLE: NVS erase failed: %s\n", esp_err_to_name(erase_err));
    return -1;
}
```

---

#### B4. USB `getchar()` 阻塞 — 超时机制失效

**文件**: `firmware/components/usb/usb_cdc_console.c:78`
**影响**: 10ms 轮询 + timeout 逻辑完全无效，读操作阻塞调用任务

```c
int c = getchar();       // ← 默认阻塞！没有数据就卡住
if (c == EOF) {
    vTaskDelay(pdMS_TO_TICKS(10));  // ← 这行根本执行不到
}
```

ESP32 的 `stdin` VFS 默认是阻塞模式。需要 `fcntl(0, F_SETFL, O_NONBLOCK)` 或配置 menuconfig 中 `CONFIG_VFS_SUPPORT_TERMIOS=1` 才能让 `getchar()` 非阻塞。

**修复**: 在 `usb_console_init` 中调用 `fcntl(0, F_SETFL, O_NONBLOCK)` 或使用 `select()` 带超时。

---

### 🟠 中等 (5 个)

#### M1. USB 读超时返回部分数据，违反 API 契约

**文件**: `usb_cdc_console.c:68-71`

```c
if (elapsed >= timeout_ms) {
    if (pos > 0) {
        buf[pos] = '\0';
        return (int)pos;     // ← 返回正数（看起来像成功）
    }
    return -503;              // ← API 文档说超时返回 -503
}
```

`usb_if.h` 明确写 `-503 if timeout`。但超时时如果已经读了一部分数据，返回正数。调用者以为成功收到了一行，实际是半行数据。

**修复**: 超时一致返回 `-503`；如果需要保留部分数据，增加单独的 `USB_ERR_TIMEOUT_PARTIAL` 错误码。

---

#### M2. `ftell` 错误返回 -1，转为 `uint32_t` 后溢出

**文件**: `littlefs_storage.c:92-93`

```c
long file_size = ftell(f);    // ← 错误时返回 -1L
if ((uint32_t)file_size > buf_len) {  // ← (uint32_t)(-1L) = 0xFFFFFFFF
```

`ftell` 在文件不存在/无权限时返回 `-1`。转为 `uint32_t` 后变成 `4294967295`。巧合地被 `buf_len` 检查捕获，但错误信息误导（"buffer too small" 而非 "read error"）。

**修复**: 先检查 `file_size < 0` 再转换。

---

#### M3. `storage_file_exists` 不加锁

**文件**: `littlefs_storage.c:127-136`

所有其他 storage 函数都拿 `s_mutex`，唯独 `storage_file_exists` 和 `storage_get_free_space` 不拿。`fopen`/`fclose` 与并发 `remove`/`fwrite` 之间存在 TOCTOU 竞态。

**修复**: 加 `xSemaphoreTake/Give`。

---

#### M4. CLI 缺少 FILTER ADD 命令

**文件**: `main/main.c:85-101`

CLI 只支持 `FILTER CLEAR` 和 `FILTER LIST`，没有 `FILTER ADD`。虽然有 `filter_add_rule()` 函数，但 CLI 用户无法调用。与 B2 叠加后，过滤功能完全不可用。

**修复**: 添加 `FILTER ADD <type> <pattern>` 命令（type: NAME/UUID/RSSI/MAC）。

---

#### M5. BLE 扫描重启时队列未清空

**文件**: `ble_scan.c:103-108`

```c
if (s_scan_queue == NULL) {
    s_scan_queue = xQueueCreate(...);
}
// ← 如果队列已存在（上次扫描残留），旧数据还在里面
```

停止→重启扫描时，上次残留的队列条目会被 pipeline 当新数据处理。

**修复**: 在 `ble_scan_start` 中调用 `xQueueReset(s_scan_queue)`。

### 🔴 致命缺口

**1. ESP32 路径从未被测试**

AD Parser 和 JSON Encoder 都有 `#ifdef ESP_PLATFORM` 双实现：
- Host 测试只覆盖了 `#else` 分支（手写 parser / snprintf encoder）

**2. 5 个模块零测试**
