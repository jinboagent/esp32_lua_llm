## I. Bug Findings — Stage 2 (BLE Core)

### 🔴 Critical (4)

#### B-S2-1. Double-deinit race in the BLE Init sync-timeout path

**File**: `firmware/components/ble/ble_nimble_init.c:89-95`
**Impact**: System crash

```c
// Error path (line 89-95):
nimble_port_stop();
nimble_port_deinit();
// Meanwhile the host task (line 34-38) is still running on another thread:
static void s_host_task(void *param) {
    nimble_port_run();           // nimble_port_stop() makes this return
    nimble_port_freertos_deinit(); // ← races with nimble_port_deinit()!
}
```

After the 2-second sync timeout, the error path frees the NimBLE structures while the host task thread is also freeing them. Two threads free the same internal structures — use-after-free / double-free.

**Fix**: The sync-timeout path should wait for the host task to exit (`vTaskDelete` or a semaphore) before calling `nimble_port_deinit()`.

---

#### B-S2-2. `s_scanning` flag modified from two FreeRTOS tasks without locking

**File**: `ble_scan.c`
**Impact**: Inconsistent scan state; may cause abnormal `ble_scan_stop` behavior

```c
// app_main task: ble_scan_start() → s_scanning = true;   (line 127)
// NimBLE host task: DISC_COMPLETE → s_scanning = false;  (line 88)
```

Two tasks read and write the same `bool` variable with no mutex/atomic protection. A classic race: the user calls `ble_scan_stop()` to cancel the GAP procedure while the NimBLE host task, reacting to the cancellation, sets `s_scanning = false` on `DISC_COMPLETE`.

**Fix**: Use `portENTER_CRITICAL` / `portEXIT_CRITICAL` or `stdatomic.h`.

---

#### B-S2-3. Race between the dedup-table `memset` and GAP callback writes

**File**: `ble_scan.c:113`
**Impact**: Dedup table corruption, null/wild pointers

```c
// ble_scan_start() — app_main task
memset(s_dedup, 0, sizeof(s_dedup));  // ← clears the dedup table

// s_gap_event_handler() — NimBLE host task (possibly on another core/priority)
memcpy(s_dedup[idx].addr, addr, 6);   // ← writes at the same time
```

After `ble_gap_disc()` is called, the NimBLE host task may immediately fire the discovery callback, racing with the memset.

**Fix**: Initialize the dedup table before calling `ble_gap_disc()`, or protect it with a critical section.

---

#### B-S2-4. Weak XOR hash causes heavy false dedup — advertisements from different devices wrongly dropped

**File**: `ble_scan.c:26-33`
**Impact**: Loss of legitimate device data

```c
static uint8_t s_dedup_hash(const uint8_t addr[6]) {
    uint8_t h = 0;
    for (int i = 0; i < 6; i++) h ^= addr[i];
    return h % BLE_DEDUP_TABLE_SIZE;  // 64 buckets
}
```

- `AA:BB:CC:DD:EE:FF` and `AA:BB:CC:DD:EE:AA` collide
- Only 64 buckets, no linked-list/linear-probing collision resolution
- On collision the entry is simply overwritten → old devices get identified as new, and new devices can also be masked by old ones

**Fix**: Use an FNV-1a hash + linear probing, or expand to 256 entries + a linked list.

## II. Bug Findings — Stage 3 (Lua Engine)

### 🔴 Critical (7)

#### B-S3-1. malloc/free instead of a static memory pool — violates the Feature Spec

**File**: `firmware/components/lua/lua_port.c:16-49`
**Impact**: ESP32 heap fragmentation → OOM after long runtimes

The feature spec (F3.1 §4, §7) explicitly requires a `pool_alloc/pool_free/pool_realloc` static pool. The implementation uses `malloc/free/realloc` directly:

```c
static void *s_l_alloc(void *ud, void *ptr, size_t osize, size_t nsize) {
    lua_alloc_ctx_t *ctx = (lua_alloc_ctx_t *)ud;
    if (nsize == 0) { free(ptr); ctx->used -= osize; return NULL; }
    void *new_ptr = realloc(ptr, nsize);  // ← generic heap allocator, not a static pool
    ...
}
```

**Fix**: Implement `pool_alloc/pool_free/pool_realloc` managing a preallocated `static uint8_t lua_heap[LUA_HEAP_SIZE]`.

---

#### B-S3-2. Sandbox bypass — blacklist approach opens everything first, then removes

**File**: `lua_port.c:114-118`
**Impact**: A malicious LLM script can restore dangerous libraries such as `debug` and `io`

```c
luaL_openlibs(L);     // opens everything (including debug, io, os, package)
lua_pushnil(L);       // merely nils them out of the globals table
lua_setglobal(L, "debug");
lua_pushnil(L);
lua_setglobal(L, "io");
// ... but the libraries are still in the Lua registry!
```

A malicious script may recover `debug.getregistry`, `debug.setupvalue`, `io.open`, etc. via registry traversal or error-object metatables:

```lua
-- what the LLM might generate:
local f = load("return debug");  -- if load is available
-- or via the registry:
for k in pairs(debug.getregistry()) do ... end
```

**Fix**: Use a whitelist approach — open only `string`, `table`, `math`, `utf8`, and do not call `luaL_openlibs`.

---

#### B-S3-3. `script_upload_end` executes the script instead of trial-compiling it — violates the Spec

**File**: `firmware/components/lua/script_mgmt.c:94-98`
**Impact**: Script executed twice (once at upload + once at run), side-channel attack

```c
int ret = lua_engine_exec(s_upload.buffer, result_buf, sizeof(result_buf));
// Spec says: "attempts a trial compile" → should call luaL_loadstring, without executing
// Actual: lua_engine_exec → luaL_loadstring + lua_pcall → fully executes
```

Attack script:
```lua
counter = (counter or 0) + 1
if counter == 1 then return "ok" end  -- upload: pretend to be benign
-- second run: trigger malicious behavior
```

**Fix**: `script_upload_end` calls `luaL_loadstring` (no execution); `script_run` calls `lua_pcall` (execution).

---

#### B-S3-4. Two FreeRTOS tasks access the same `lua_State` without locking

**File**: `lua_port.c` + `scan_pipeline.c` + `main/main.c`
**Impact**: VM stack corrupted → crash or undefined behavior

| Task | Access | When |
|------|------|------|
| Pipeline task | `lua_engine_call_on_adv/transform` | every BLE advertisement |
| app_main task | `lua_engine_exec` (LUA EXEC command) | user-triggered |

The Lua VM is inherently not thread-safe. If the pipeline is executing hook callbacks while a script is being uploaded, the VM stack and globals table are modified by two tasks at once.

**Fix**: Add a mutex at every Lua API entry point, or pause script execution while the pipeline is running.

---

#### B-S3-5. Hook call functions lack NULL pointer checks

**File**: `lua_port.c:244, 289`

```c
int lua_engine_call_on_adv(const char *func_name, ...) {
    lua_getglobal(L, func_name);  // ← no check for func_name != NULL
```
By contrast, `lua_engine_has_func:231` correctly checks for NULL. `lua_getglobal(L, NULL)` crashes the Lua VM.

---

#### B-S3-6. Filter engine in `main.c` accessed concurrently from CLI and Pipeline tasks without locking

**File**: `main/main.c:85-101` + `scan_pipeline.c:51`
**Impact**: Rule array corruption; `filter_evaluate` reads half-updated rules

```c
// app_main: FILTER ADD → filter_add_rule → eng->rule_count++ + memcpy rule
// Pipeline: filter_evaluate → for (i < eng->rule_count) → may read partially written data
```

Similar to B-S3-4 — shared data unprotected by locks.

---

#### B-S3-7. SCAN START partial failure does not roll back

**File**: `main/main.c:61-71`

```c
int ret1 = ble_scan_start();
int ret2 = pipeline_start();
if (ret1 == 0 && ret2 == 0) { /* success */ }
// ret1=0, ret2!=0 → scan runs with no pipeline consumer → queue keeps building up
// ret1!=0, ret2=0 → pipeline spins polling idly
```

The two operations should be atomic, or roll back on failure.

## III. Summary of Cross-Stage Concurrency Issues (the most severe architectural flaw)

Three shared data structures accessed without locks from three FreeRTOS tasks:

```
app_main task      → filter_add_rule, filter_clear, lua_engine_exec, script_upload_end
Pipeline task      → filter_evaluate, lua_engine_call_on_adv, lua_engine_call_transform
NimBLE host task   → s_scanning, s_dedup (GAP callback context)
```

| Shared data | Accessed by | Risk level | Consequence |
|----------|--------|:--------:|------|
| `lua_State` | app_main + Pipeline | 🔴 Critical | VM stack corrupted → crash |
| `filter_engine_t` | app_main + Pipeline | 🔴 Critical | rule array corrupted → undefined behavior |
| `s_scanning` | app_main + NimBLE host | 🟠 Medium | inconsistent scan state |
| `s_dedup[]` | app_main (memset) + NimBLE host (write) | 🟠 Medium | dedup table corrupted |

**Root cause**: `lua_if.h`, `filter_if.h`, and `ble_if.h` all fail to declare thread-safety semantics. Callers have no way to know which function can safely be called from which task context.
