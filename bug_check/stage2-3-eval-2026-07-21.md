## 一、Bug 发现 — Stage 2 (BLE Core)

### 🔴 严重 (4 个)

#### B-S2-1. BLE Init 同步超时路径存在 double-deinit 竞态

**文件**: `firmware/components/ble/ble_nimble_init.c:89-95`
**影响**: 系统崩溃

```c
// 错误路径 (line 89-95):
nimble_port_stop();
nimble_port_deinit();
// 同时 host task (line 34-38) 仍在另一个线程运行:
static void s_host_task(void *param) {
    nimble_port_run();           // nimble_port_stop() 使此返回
    nimble_port_freertos_deinit(); // ← 与 nimble_port_deinit() 竞态!
}
```

2 秒同步超时后，错误路径释放 NimBLE 结构，同时 host task 线程也在释放。两个线程释放同一内部结构 — use-after-free / double-free。

**修复**: 同步超时路径应等待 host task 退出（`vTaskDelete` 或信号量）后再调用 `nimble_port_deinit()`。

---

#### B-S2-2. `s_scanning` 标志从两个 FreeRTOS 任务无锁修改

**文件**: `ble_scan.c`
**影响**: 扫描状态不一致，可能导致 `ble_scan_stop` 行为异常

```c
// app_main 任务: ble_scan_start() → s_scanning = true;   (line 127)
// NimBLE host 任务: DISC_COMPLETE → s_scanning = false;  (line 88)
```

两个任务读写同一 `bool` 变量，无 mutex/atomic 保护。典型的竞态：用户调用 `ble_scan_stop()` 取消 GAP procedure，同时 NimBLE host 任务因取消触发 `DISC_COMPLETE` 设置 `s_scanning = false`。

**修复**: 使用 `portENTER_CRITICAL` / `portEXIT_CRITICAL` 或 `stdatomic.h`。

---

#### B-S2-3. Dedup 表 `memset` 与 GAP 回调写入竞态

**文件**: `ble_scan.c:113`
**影响**: 去重表损坏、空指针/野指针

```c
// ble_scan_start() — app_main 任务
memset(s_dedup, 0, sizeof(s_dedup));  // ← 清空去重表

// s_gap_event_handler() — NimBLE host 任务 (可能在另一个核心/优先级)
memcpy(s_dedup[idx].addr, addr, 6);   // ← 同时写入
```

`ble_gap_disc()` 调用后 NimBLE host task 可能立即触发 discovery 回调，与 memset 竞态。

**修复**: 在 `ble_gap_disc()` 调用前初始化去重表，或使用临界区保护。

---

#### B-S2-4. 弱 XOR 哈希导致大量假去重 — 不同设备的广告被错误丢弃

**文件**: `ble_scan.c:26-33`
**影响**: 合法设备数据丢失

```c
static uint8_t s_dedup_hash(const uint8_t addr[6]) {
    uint8_t h = 0;
    for (int i = 0; i < 6; i++) h ^= addr[i];
    return h % BLE_DEDUP_TABLE_SIZE;  // 64 桶
}
```

- `AA:BB:CC:DD:EE:FF` 和 `AA:BB:CC:DD:EE:AA` 哈希碰撞
- 只有 64 个桶，无链表/线性探测冲突解决
- 碰撞时直接覆盖 → 旧设备被识别为新设备，新设备也可能被旧设备掩盖

**修复**: 使用 FNV-1a 哈希 + 线性探测，或扩大到 256 条目 + 链表。

## 二、Bug 发现 — Stage 3 (Lua Engine)

### 🔴 严重 (7 个)

#### B-S3-1. malloc/free 代替静态内存池 — 违反 Feature Spec

**文件**: `firmware/components/lua/lua_port.c:16-49`
**影响**: ESP32 堆碎片化 → 长时间运行后 OOM

Feature spec (F3.1 §4, §7) 明确要求 `pool_alloc/pool_free/pool_realloc` 静态池。实现直接用 `malloc/free/realloc`:

```c
static void *s_l_alloc(void *ud, void *ptr, size_t osize, size_t nsize) {
    lua_alloc_ctx_t *ctx = (lua_alloc_ctx_t *)ud;
    if (nsize == 0) { free(ptr); ctx->used -= osize; return NULL; }
    void *new_ptr = realloc(ptr, nsize);  // ← 通用堆分配器，非静态池
    ...
}
```

**修复**: 实现 `pool_alloc/pool_free/pool_realloc` 管理预分配的 `static uint8_t lua_heap[LUA_HEAP_SIZE]`。

---

#### B-S3-2. 沙箱旁路 — 黑名单模式先全部打开再删除

**文件**: `lua_port.c:114-118`
**影响**: 恶意 LLM 脚本可恢复 `debug`、`io` 等危险库

```c
luaL_openlibs(L);     // 全部打开（含 debug, io, os, package）
lua_pushnil(L);       // 仅从全局表 nil
lua_setglobal(L, "debug");
lua_pushnil(L);
lua_setglobal(L, "io");
// ... 但库仍在 Lua registry 中！
```

恶意脚本可能通过 registry 遍历或错误对象 metatable 恢复 `debug.getregistry`、`debug.setupvalue`、`io.open` 等:

```lua
-- LLM 可能生成：
local f = load("return debug");  -- 若 load 可用
-- 或通过 registry:
for k in pairs(debug.getregistry()) do ... end
```

**修复**: 使用白名单模式 — 只打开 `string`、`table`、`math`、`utf8`，不调用 `luaL_openlibs`。

---

#### B-S3-3. `script_upload_end` 执行脚本而非试编译 — 违反 Spec

**文件**: `firmware/components/lua/script_mgmt.c:94-98`
**影响**: 脚本双重执行（上传时一次 + run 时一次），侧信道攻击

```c
int ret = lua_engine_exec(s_upload.buffer, result_buf, sizeof(result_buf));
// Spec 说: "attempts a trial compile" → 应调用 luaL_loadstring，不执行
// 实际: lua_engine_exec → luaL_loadstring + lua_pcall → 完全执行
```

攻击脚本:
```lua
counter = (counter or 0) + 1
if counter == 1 then return "ok" end  -- 上传: 假装正常
-- 第二次运行: 触发恶意行为
```

**修复**: `script_upload_end` 调用 `luaL_loadstring` (不执行)，`script_run` 调用 `lua_pcall` (执行)。

---

#### B-S3-4. 两个 FreeRTOS 任务无锁访问同一个 `lua_State`

**文件**: `lua_port.c` + `scan_pipeline.c` + `main/main.c`
**影响**: VM 栈被破坏 → 崩溃或未定义行为

| 任务 | 访问 | 何时 |
|------|------|------|
| Pipeline 任务 | `lua_engine_call_on_adv/transform` | 每条 BLE 广播 |
| app_main 任务 | `lua_engine_exec` (LUA EXEC 命令) | 用户触发 |

Lua VM 本质非线程安全。上传脚本时若 pipeline 正在执行 hook 回调，VM 栈、全局表同时被两个任务修改。

**修复**: 所有 Lua API 入口加 mutex，或 pipeline 在执行期间暂停脚本执行。

---

#### B-S3-5. Hook 调用函数缺少 NULL 指针检查

**文件**: `lua_port.c:244, 289`

```c
int lua_engine_call_on_adv(const char *func_name, ...) {
    lua_getglobal(L, func_name);  // ← 未检查 func_name != NULL
```
对比 `lua_engine_has_func:231` 正确检查了 NULL。`lua_getglobal(L, NULL)` 导致 Lua VM 崩溃。

---

#### B-S3-6. `main.c` 中 filter engine 从 CLI 和 Pipeline 双任务无锁并发访问

**文件**: `main/main.c:85-101` + `scan_pipeline.c:51`
**影响**: Rule 数组损坏、`filter_evaluate` 读到半更新的 rule

```c
// app_main: FILTER ADD → filter_add_rule → eng->rule_count++ + memcpy rule
// Pipeline: filter_evaluate → for (i < eng->rule_count) → 可能读到部分写入
```

与 B-S3-4 类似 — 共享数据无锁保护。

---

#### B-S3-7. SCAN START 部分失败不回滚

**文件**: `main/main.c:61-71`

```c
int ret1 = ble_scan_start();
int ret2 = pipeline_start();
if (ret1 == 0 && ret2 == 0) { /* 成功 */ }
// ret1=0, ret2=非0 → 扫描运行但无 pipeline 消费 → 队列堆积
// ret1=非0, ret2=0 → pipeline 空转轮询
```

两个操作应该原子化，或失败时回滚。

## 三、跨 Stage 的并发问题汇总 (最严重架构缺陷)

3 个共享数据结构从 3 个 FreeRTOS 任务无锁访问：

```
app_main 任务      → filter_add_rule, filter_clear, lua_engine_exec, script_upload_end
Pipeline 任务      → filter_evaluate, lua_engine_call_on_adv, lua_engine_call_transform
NimBLE host 任务   → s_scanning, s_dedup (GAP 回调上下文)
```

| 共享数据 | 访问者 | 风险等级 | 后果 |
|----------|--------|:--------:|------|
| `lua_State` | app_main + Pipeline | 🔴 严重 | VM 栈破坏 → 崩溃 |
| `filter_engine_t` | app_main + Pipeline | 🔴 严重 | Rule 数组损坏 → 未定义行为 |
| `s_scanning` | app_main + NimBLE host | 🟠 中等 | 扫描状态不一致 |
| `s_dedup[]` | app_main (memset) + NimBLE host (写) | 🟠 中等 | 去重表损坏 |

**根本原因**: `lua_if.h`、`filter_if.h`、`ble_if.h` 均未声明线程安全语义。调用者不知道哪个函数可以在哪个任务上下文安全调用。
