## N1. `s_encode_string_escaped` 循环守卫不匹配 `\uXXXX` 转义长度

- **文件**: `firmware/components/json_enc/json_encoder.c:18`
- **严重度**: 🟡 低（当前场景不可触发，但函数契约不安全）

```c
for (const char *p = str; *p != '\0' && pos + 2 < buf_len; p++) {
```

循环守卫 `pos + 2 < buf_len` 仅保证 1 个普通字符 + `\0` 的空间。但 `< 0x20` 的控制字符需要 **6 字节**（`\uXXXX` + `\0`）。如果 `buf_len - pos` = 3~5 且遇到控制字符：

- `snprintf` 部分写入 → 返回 6 → 检测到截断 → 返回 -203
- 但缓冲区已留下不完整的 `\u00` 前缀

**根因**: 函数内部不同转义路径对剩余空间的需求不对称（2 vs 6 字节），循环守卫只覆盖最短路径。

**触发条件**: 当前 `escaped_name[193]` 远大于最坏需求（187），实际不可触发。但若未来调用者传入更小缓冲区，可能产生部分输出。

**修复建议**: 将循环守卫改为 `pos + 6 < buf_len`，或在 `\uXXXX` 分支前单独检查剩余空间。

## N2. LittleFS 分区使用错误的 subtype

- **文件**: `partitions.csv:5`
- **严重度**: 🟡 低

```csv
littlefs, data, spiffs,  0x190000,0x10000,
```

subtype 写的是 `spiffs`，实际应为 `littlefs`。ESP-IDF 出于向后兼容接受 `spiffs`，但：
- 语义错误，误导未来维护者
- 若 ESP-IDF 未来版本移除兼容逻辑，分区将无法识别

**修复建议**: `spiffs` → `littlefs`

## N3. `s_encode_mac` 错误检查的语义污染

- **文件**: `firmware/components/json_enc/json_encoder.c:68-69`
- **严重度**: 🟡 低（仅影响错误路径的错误码语义）

```c
int mac_ret = s_encode_mac(mac_str, sizeof(mac_str), report->addr);
if (mac_ret < 0) return mac_ret;
```

`s_encode_mac` 对固定的 18 字节缓冲区 + 17 字符固定输出**不可能失败**。但如果它失败：
- 返回的是 `-203`（buffer too small）
- `json_encode_adv` 调用者会误以为是**主输出缓冲区**不够大
- 实际是内部 MAC 转义栈缓冲区问题

**修复建议**: 若保留此检查，应返回专用内部错误码（如 `-200` general failure），而非将子函数错误码直接透传。

## N4. `escaped_name` 溢出的错误码同样语义污染

- **文件**: `firmware/components/json_enc/json_encoder.c:88-89`
- **严重度**: 🟡 低（当前不可触发）

```c
int esc_ret = s_encode_string_escaped(escaped_name, sizeof(escaped_name), report->name);
if (esc_ret < 0) return esc_ret;
```

同 N3：若 `escaped_name` 溢出（当前 193 字节 > 最坏 187 字节，实际不会发生），透传的 `-203` 会让调用者误判为主输出缓冲区问题。

**修复建议**: 同上，使用独立的内部错误码。

## N5. `build.bat` 缺少 `set-target` 步骤

- **文件**: `build.bat:4`
- **严重度**: 🟠 中等

```batch
@echo off
call C:\Espressif\idf_cmd_init.bat
cd /d E:\agent\esp32_lua_llm
idf.py build
```

未先执行 `idf.py set-target esp32s3`。场景：
- 首次构建或 `build/` 目录被清理后，目标未设置
- `idf.py build` 会因缺少目标配置而失败

**修复建议**: 在 `idf.py build` 前添加 `idf.py set-target esp32s3`

---

## N6. `flash.bat` / `monitor.bat` 硬编码 COM12

- **文件**: `flash.bat:4`, `monitor.bat:4`
- **严重度**: 🟠 中等

```batch
idf.py -p COM12 flash
idf.py -p COM12 monitor
```

- 不同机器、不同 USB 口的 COM 编号不同
- COM12 在其他环境下几乎必定失败，且错误信息不直观

**修复建议**:
- 方案 A：改为 `idf.py flash` / `idf.py monitor`，由 ESP-IDF 自动检测串口
- 方案 B：接受 `%1` 参数传入 COM 口编号
