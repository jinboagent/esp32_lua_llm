## N1. `s_encode_string_escaped` loop guard does not match the `\uXXXX` escape length

- **File**: `firmware/components/json_enc/json_encoder.c:18`
- **Severity**: 🟡 Low (not triggerable in the current scenario, but the function contract is unsafe)

```c
for (const char *p = str; *p != '\0' && pos + 2 < buf_len; p++) {
```

The loop guard `pos + 2 < buf_len` only guarantees space for 1 ordinary character + `\0`. But a control character `< 0x20` needs **6 bytes** (`\uXXXX` + `\0`). If `buf_len - pos` = 3~5 and a control character is encountered:

- `snprintf` writes partially → returns 6 → truncation detected → returns -203
- but the buffer is left with an incomplete `\u00` prefix

**Root cause**: the function's different escape paths have asymmetric requirements for the remaining space (2 vs 6 bytes), and the loop guard only covers the shortest path.

**Trigger condition**: the current `escaped_name[193]` is far larger than the worst-case requirement (187), so this cannot actually be triggered. But if a future caller passes a smaller buffer, partial output may be produced.

**Fix recommendation**: change the loop guard to `pos + 6 < buf_len`, or check the remaining space separately before the `\uXXXX` branch.

## N2. LittleFS partition uses the wrong subtype

- **File**: `partitions.csv:5`
- **Severity**: 🟡 Low

```csv
littlefs, data, spiffs,  0x190000,0x10000,
```

The subtype is written as `spiffs` but should actually be `littlefs`. ESP-IDF accepts `spiffs` for backward compatibility, however:
- it is semantically wrong and misleads future maintainers
- if a future ESP-IDF version removes the compatibility logic, the partition will fail to be recognized

**Fix recommendation**: `spiffs` → `littlefs`

## N3. Semantic pollution in the `s_encode_mac` error check

- **File**: `firmware/components/json_enc/json_encoder.c:68-69`
- **Severity**: 🟡 Low (only affects the error-code semantics of the error path)

```c
int mac_ret = s_encode_mac(mac_str, sizeof(mac_str), report->addr);
if (mac_ret < 0) return mac_ret;
```

`s_encode_mac` with a fixed 18-byte buffer + fixed 17-character output **cannot possibly fail**. But if it did fail:
- it returns `-203` (buffer too small)
- callers of `json_encode_adv` would mistakenly think the **main output buffer** was not big enough
- when it is actually a problem with the internal MAC escape stack buffer

**Fix recommendation**: if this check is kept, it should return a dedicated internal error code (e.g. `-200` general failure) instead of passing the sub-function's error code straight through.

## N4. The `escaped_name` overflow error code has the same semantic pollution

- **File**: `firmware/components/json_enc/json_encoder.c:88-89`
- **Severity**: 🟡 Low (not currently triggerable)

```c
int esc_ret = s_encode_string_escaped(escaped_name, sizeof(escaped_name), report->name);
if (esc_ret < 0) return esc_ret;
```

Same as N3: if `escaped_name` overflowed (currently 193 bytes > worst-case 187 bytes, so it cannot actually happen), the passed-through `-203` would make the caller misdiagnose it as a main output buffer problem.

**Fix recommendation**: same as above, use a separate internal error code.

## N5. `build.bat` lacks the `set-target` step

- **File**: `build.bat:4`
- **Severity**: 🟠 Medium

```batch
@echo off
call C:\Espressif\idf_cmd_init.bat
cd /d E:\agent\esp32_lua_llm
idf.py build
```

`idf.py set-target esp32s3` is not run first. Scenario:
- on a first build, or after the `build/` directory is cleaned, the target is not set
- `idf.py build` fails due to the missing target configuration

**Fix recommendation**: add `idf.py set-target esp32s3` before `idf.py build`

---

## N6. `flash.bat` / `monitor.bat` hardcode COM12

- **File**: `flash.bat:4`, `monitor.bat:4`
- **Severity**: 🟠 Medium

```batch
idf.py -p COM12 flash
idf.py -p COM12 monitor
```

- COM port numbers differ across machines and USB ports
- COM12 will almost certainly fail in other environments, and the error message is not intuitive

**Fix recommendations**:
- Option A: change to `idf.py flash` / `idf.py monitor` and let ESP-IDF auto-detect the serial port
- Option B: accept the COM port number via a `%1` argument
