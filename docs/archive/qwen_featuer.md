# ESP32-S3 BLE Sniffer Dongle — Project Plan

## 1. Product Overview

### What It Is
A USB dongle based on ESP32-S3 that passively scans BLE advertisements, processes them through a filter/transform engine (with optional Lua scripting), and outputs structured JSON lines over USB CDC serial to a host PC.

### Target User
IoT developers debugging their own BLE peripherals and sensors.

### Core Value Proposition
An AI-driven BLE analysis loop:
1. **ESP32 dongle** scans BLE environment → sends raw advertisement data to PC
2. **LLM on host PC** analyzes the BLE data stream
3. **LLM generates Lua scripts** → deployed back to the ESP32 via USB
4. **ESP32 executes Lua scripts** → filters, parses, and transforms BLE data intelligently
5. **Clean, structured output** flows back to the PC for display or further analysis

### Product Architecture

```
┌─────────────────┐      USB CDC (JSON lines)      ┌──────────────────┐
│   Host PC        │ ◄───────────────────────────── │   ESP32-S3       │
│                  │     BLE advertisement stream    │   Dongle         │
│   LLM analyzes   │                                │                  │
│   BLE data       │                                │   Captures BLE   │
│                  │ ──────────────────────────────► │   advertisements │
│   LLM generates  │     Lua script (text)          │                  │
│   Lua script     │     (deployed to device)       │   Executes Lua   │
│                  │                                │   filter/transform│
└──────────────────┘                                └──────────────────┘
```

## 3. Key Design Decisions

| Decision | Choice | Rationale |
|----------|--------|-----------|
| **BLE capture scope** | Advertisements only (passive scan) | Simpler, lower memory, sufficient for v1. Connections added in v2. |
| **Host interface** | USB CDC serial | Universal, no driver needed, works with any terminal/PC app |
| **Output format** | JSON lines | LLM-native, universally parseable, self-describing, extensible |
| **Lua scope** | Filter + transform only | Users define filter rules and data transforms. Output format is fixed JSON. Simpler and safer. |
| **Lua role** | On-device scripting | Lua scripts generated by LLM on host, deployed to ESP32 to customize BLE data processing |
| **LLM path** | Via host PC | Dongle sends raw data over USB, PC runs companion app that calls LLM API |
| **Documentation language** | English | Better for AI agents and international tooling |

## 4. USB Protocol Design

### Output (ESP32 → PC): JSON Lines

Each line = one BLE advertisement:

```json
{"ts":1620000000,"addr":"AA:BB:CC:DD:EE:FF","type":"public","rssi":-45,"name":"Sensor_A","uuids":["180A","180F"],"manu":{"id":"004C","data":"01020304"}}
```

| Field | Type | Description |
|-------|------|-------------|
| `ts` | uint32 | Milliseconds since device boot |
| `addr` | string | BLE MAC address (XX:XX:XX:XX:XX:XX) |
| `type` | string | Address type: "public" or "random" |
| `rssi` | int8 | Signal strength in dBm |
| `name` | string\|null | Device name from AD, null if absent |
| `uuids` | string[] | List of 16-bit service UUIDs as hex strings |
| `manu` | object\|null | Manufacturer data: `{"id":"XXXX","data":"..."}` or null |

### Input (PC → ESP32): Text Commands

```
SCAN START                  → begin passive scanning
SCAN STOP                   → stop scanning
SCAN INTERVAL <ms>          → set scan interval
FILTER ADD name <pattern>   → add name filter (supports *)
FILTER ADD uuid <uuid>      → add UUID filter
FILTER ADD rssi <threshold> → add RSSI threshold filter
FILTER ADD mac <address>    → add MAC address filter
FILTER CLEAR                → remove all filters
FILTER LIST                 → show active filters
SCRIPT LOAD                 → begin receiving Lua script
<script lines...>
SCRIPT END                  → finish receiving, save script
SCRIPT RUN                  → execute loaded script
SCRIPT STOP                 → stop running script
STATUS                      → report current state
```

## 8. Coding Rules Summary

### Error Codes

| Code | Meaning |
|------|---------|
| 0 | Success |
| -1 | General failure |
| -2 | Invalid parameter |
| -3 | NULL pointer |
| -4 | Buffer too small |
| -5 | Timeout |
| -6 | Not initialized |
| -7 | Already initialized |
| -8 | Resource busy |
| -9 | Not found |
| -10 | Out of memory |
| -11 | Invalid state |
| -12 | Length error |

### Memory Rules
- **No malloc/free** — all static buffers or stack allocation
- All pointer parameters must be NULL-checked
- All array operations must be length-checked
- If PSRAM available: Lua scripts/data may use `heap_caps_malloc(size, MALLOC_CAP_SPIRAM)`

### Naming Conventions
- Internal functions: `static` with `s_<module>_<action>` prefix
- Public functions: `<module>_<action>` prefix (e.g., `proto_parse_adv`, `ble_scan_start`)
- Structs: `<module>_<name>_t`
- Enums: `<module>_<name>_e` with `MODULE_<ENUM_VALUE>` members
- Macros: `MODULE_<NAME>` (all caps)

### Layering Rules
- Upper layers depend on lower layers only
- No reverse dependencies
- No cross-layer dependencies (go through `interfaces/`)

### Platform Constraints
- ESP-IDF v5.x + NimBLE
- C language (C11 standard)
- No C++ in firmware components
- No WiFi stack in v1 (keep binary small)

## 9. Testing Strategy

| Level | Scope | Method | When |
|-------|-------|--------|------|
| **Unit** | AD parser, JSON encoder, filter engine | Host-side compilation (cmake), Unity framework | Every commit |
| **Integration** | USB protocol, script upload, scan pipeline | On-target, automated via PC serial script | Every feature complete |
| **End-to-end** | Full pipeline: BLE → JSON on PC | Manual with real BLE devices | Every stage complete |

### Test Priority
1. All exception/error paths (NULL, overflow, invalid state)
2. Normal operation with valid data
3. Edge cases (empty advertisement, max-length name, zero UUIDs)
4. Performance (parse time < 1ms, JSON encode time < 0.5ms)

## 10. AI-Assisted Development Workflow

### Per-Feature Process
1. **Feed context**: global coding rules (1 page) + single feature doc
2. **AI confirms**: restate requirements before coding
3. **Generate header**: `interfaces/xxx_if.h` → human review
4. **Generate implementation**: `firmware/components/xxx/xxx.c`
5. **Generate tests**: `tests/test_xxx.c` using Unity
6. **Verify**: run tests, all pass → commit
7. **Update knowledge base**: record lessons in `harness/02-knowledge/`

### Rules
- One feature at a time — no parallel features
- Interface review before implementation — never skip
- Requirements changes → update doc first, then code
- Never feed multiple features to AI at once
